# Publishing YouTune

This guide covers the manual publishing path for the current YouTune Chromium source. The same `prototype` source is intended for Chrome and Edge, but each store has its own developer account, listing, privacy declarations, and review process.

## 1. Build the package

From the repository root on Linux or macOS:

```bash
npm test
npm run build -- 0.2.3
```

On Windows PowerShell:

```powershell
npm test
powershell -ExecutionPolicy Bypass -File .\scripts\build.ps1 0.2.3
```

The output is `dist/youtune-0.2.3.zip`. The store package contains only the runtime extension files, icons, and manifest required by the browser. Development validators, laboratory files, reports, source archives, and repository documentation are excluded. Upload the ZIP, not the repository root.

## 2. Test before submission

Load the `prototype` directory unpacked in both Chrome and Edge. Test YouTube and YouTube Music playback manually using `reports/reliability-test-matrix.md`. Do not submit while any scenario produces silence, duplicate audio, settings loss, or an unexplained permission request.

Use the browser's extension inspection tools to review the final manifest and service worker. Confirm that there is no remote code, no unexpected network request, and no accidental development file in the ZIP.

## 3. Chrome Web Store

Open the [Chrome Developer Dashboard](https://chrome.google.com/webstore/devconsole), sign in, create a new item, and upload the ZIP generated by the build script. Google's publishing guide describes the upload flow as choosing **Add new item**, selecting the ZIP, and uploading it. The dashboard then exposes the Package, Store Listing, Privacy, Distribution, and Test instructions sections.[1]

For YouTune, the privacy declaration must match the actual source. The current implementation stores settings locally and does not upload audio. State the extension's single purpose as personal audio adjustment for YouTube and YouTube Music. Explain why the YouTube host permissions are required. Do not claim that the extension supports features that are still experimental or not active in the source.

A practical first listing should include a clear icon, screenshots of the popup and in-page behavior, a short description, a longer description, support contact details, and a privacy policy URL if the dashboard requires one for the selected declarations. Use a real support URL or repository issue page that you will maintain.

## 4. Microsoft Edge Add-ons

Open the [Microsoft Edge Partner Center](https://partner.microsoft.com/dashboard/microsoftedge/overview), register as an extension developer, create a new extension, and upload the ZIP. Microsoft's current publishing guide says the package must include the manifest and required images or other files, and that the manifest name, description, and short description feed into the listing.[2]

Complete availability, properties, privacy, store listing, language, search-term, and certification-testing fields. In the privacy section, state YouTune's purpose, justify the YouTube host permissions and storage permission, declare whether remote code is used, certify data practices, and provide a privacy policy when required. The current source contains no remote code and no audio upload path.

For certification notes, provide exact test steps: install the unpacked build, open a YouTube video, start playback, open YouTune, select a preset, change a slider, use bypass, navigate to another video, and confirm that audio remains audible. Also mention the YouTube Music track-change test.

## 5. Version updates

Increase the version in `prototype/manifest.json` and `package.json`, run the full validation suite, build a new ZIP, and submit the new package through each store dashboard. Keep a short changelog in the GitHub release. Never overwrite a released package without a corresponding version change.

## 6. Store-risk checklist

Before submission, confirm that the final bundle contains no test audio, private tokens, local absolute paths, benchmark artifacts, development ZIPs, or unused permission declarations. Confirm that the listing does not make clinical, hearing-protection, or guaranteed sound-quality claims. Describe the output safety stage accurately as a conservative prototype unless it has been upgraded and tested as a production limiter.

The first public release should disable experimental bass enhancement, crossfeed, loudness normalization, and headphone-profile bundling unless each has passed its own quality and licensing gate.
